# Тестовое задание «Системный аналитик»: модуль ККД по целям сотрудников

Кейс Сбера («Фабрика решений»): контроль качества данных (ККД) по целям и ключевым результатам.
Модуль раз в неделю проверяет цели и КР в PostgreSQL набором правил, считает метрики с учётом
каскада и показывает дельту с прошлым прогоном. Здесь — спецификация для разработки и SQL к ней,
проверенный на настоящем PostgreSQL.

- **Сдаваемый документ:** [SA_KKD_spec.pdf](SA_KKD_spec.pdf)
- Исходник: [docs/SA_KKD_spec.md](docs/SA_KKD_spec.md)
- SQL: [sql/](sql/) — DDL, правила, метрики, дельта, запросы API, откат, тесты

Термины, коды правил и формат ошибок взяты из эталонного mock API команды (moc_api_kkd), чтобы спецификация
совпадала с тем, что ждёт фронтенд.

## Как проверялся SQL

Весь SQL выполнен на **PostgreSQL 18.6** через [PGlite](https://pglite.dev) — это PostgreSQL, собранный
в WebAssembly; сервер ставить не нужно (пакет `pgserver` для Python не нашёлся под Windows
и Python 3.13).

```bash
npm install --no-save @electric-sql/pglite
node sql/test/run_pglite.mjs          # 60 проверок, в конце "rollback: kkd objects left = 0"
python sql/test/check_spec_sql.py     # SQL в спецификации = SQL в sql/ (8 блоков, 0 расхождений)
```

Что делает прогон: накат схемы → откат (`99_kkd_rollback.sql`) → повторный накат (как в условиях приёмки
из бизнес-требований), тестовые данные (`test/10_test_data.sql`), 5 прогонов ККД с проверками `ASSERT`
(`test/20_test_scenario.sql`), финальный откат. Проверяются граничные случаи из спецификации: веса
99.5 / 100 / 100.5, ровно 45 и 46 дней, часовой пояс, цель без КР, цель уровня блока, родитель-черновик,
подразделение без целей, первый и упавший прогон, вернувшаяся проблема, выключенное правило,
два прогона одновременно, зависший прогон.

С обычным PostgreSQL (≥ 13) — те же файлы через `psql -v ON_ERROR_STOP=1 -f` в порядке
`00, 01, 02, 03, test/10, test/20`.

## Ключевые решения

**Простыми словами.** Спецификация описывает, как найти ошибки в целях, которые сотрудники заводят криво: цель без КР,
веса КР не дают 100%, цель не привязана к цели начальника, факт месяцами не обновляют. Модуль ККД раз
в неделю делает «прогон»: проверяет все активные цели четырьмя правилами, записывает найденные проблемы
и считает по каждому подразделению три цифры — долю корректных целей, покрытие каскадом и число проблем.
Потом сравнивает с прошлым успешным прогоном: какие проблемы новые, какие остались, какие исправили.
Я как аналитик описал это так, чтобы разработчик мог написать код без вопросов: таблицы, правила с SQL,
формулы, ответы API и что делать в каждом неудобном случае. И сам проверил SQL на базе.

**Вероятные вопросы**

1. **Почему проблема определяется по fingerprint `RULE_CODE:object_id`?** Каждый прогон проблемы находятся
   заново, и номера строк в базе каждый раз разные. А правило и объект от прогона к прогону те же, поэтому
   их пара — естественный ключ: совпала пара — та же проблема. Детали в ключ не входят: если сумма весов
   была 90, а стала 110, это та же незакрытая проблема.
2. **Почему `null`, а не 0, когда считать не из чего?** Ноль — это результат («ни одной корректной цели»),
   а `null` — «нет данных». Если в новом отделе нет целей, 0% выглядел бы как провал, а «0 проблем» — как
   отличник. Оба неправда, поэтому `null`, и интерфейс пишет «нет активных целей».
3. **Почему сравниваем с последним успешным прогоном, а не просто с предыдущим?** У упавшего прогона нет
   результатов: всё пишется одной транзакцией и при ошибке откатывается. Сравнивать с пустотой нельзя —
   все проблемы стали бы «новыми». Поэтому упавший пропускаем, а в ответе явно пишем, с каким прогоном
   сравнили.
4. **Как каскад учитывается в метриках?** Двумя способами. Первый — по оргструктуре: метрика департамента
   считается по всем целям департамента и его отделов (рекурсивный запрос по дереву), причём по объединению
   целей, а не как среднее процентов отделов: отдел из 2 целей не должен весить столько же, сколько отдел
   из 50. Второй — отдельная метрика «Покрытие каскадом»: какая доля целей ниже уровня блока привязана
   к вышестоящей цели.
5. **Почему именно эти 4 правила?** Они закрывают четыре разных вида брака: структура цели (нет КР),
   арифметика (веса), каскад (нет родителя — обязательное по заданию), свежесть данных (факт не обновляют).
   И у них три разных уровня важности. Остальные 8 правил эталона подключаются тем же механизмом:
   строка в справочнике и один `SELECT`.
6. **Что такое активная цель?** Только `status = 'active'`. Черновики, закрытые и отменённые не проверяются
   и в метрики не входят: черновик ещё не обязан быть правильным, а закрытую уже не исправляют.
7. **Почему метрики прошлых прогонов хранятся, а не пересчитываются?** Данные целей всё время меняются.
   Чтобы показать «было 75%, стало 76%», нужно значение на дату прошлого прогона — пересчитать его уже нельзя.
8. **Почему знак дельты — это не «лучше/хуже»?** У доли корректных целей рост — хорошо, у числа проблем —
   плохо. Поэтому у метрики есть признак `higher_is_better`, и `trend` считается с его учётом.
9. **Что будет, если прогон ещё идёт?** Страница по умолчанию показывает последний завершённый прогон.
   Если явно запросить идущий — ответ 409 `RUN_IN_PROGRESS`. Два прогона одновременно запустить нельзя —
   это держит уникальный индекс в базе, а не только код.
10. **Граничный случай «ровно 45 дней» — нарушение?** Нет: нарушение — больше 45, то есть с 46-го дня.
    Дни считаются по московской дате, это тоже проверено тестом.
